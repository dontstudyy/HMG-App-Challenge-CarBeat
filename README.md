# 카비트 (CarBeat)

차를 세워 둔 시간에 브레이크 페달, 핸들, 와이퍼 스위치로 박자를 맞추고, 맞힐 때마다 앰비언트 라이트·와이퍼·실내등이 반응하는 차량 조작계 리듬게임입니다.

- 현대 Pleos Connect 앱 공모전 출품작
- 대상 환경: Android(Kotlin) / Pleos Connect SDK
- 상태: 개발 중

## 검증 기록

Pleos Connect 에뮬레이터(AVD `Pleos_Connect_v2.1.0`, 2560×1440, 160dpi)에서 측정했다. 측정 스크립트는 `tools/exp_input.py`, 앱 쪽 실험 코드는 debug 빌드 전용(`app/src/debug`)이다.

### 단계 0 (2026-11-13)

입력 지연은 Virtual Console REST 전송 시각 → 앱 리스너 도착 시각이다. PC와 에뮬레이터의 시계 차이(약 ±60ms)가 절대값에 섞이므로 **흔들림(범위, 중앙값에서 최대 벗어남)만 의미가 있다.**

| 항목 | 결과 |
|---|---|
| 브레이크 입력 (20회) | 범위 55ms, 표준편차 12ms, 중앙값에서 최대 51ms. 해제도 즉시 반영 |
| 핸들 임계값 통과 시각 (20회) | 범위 204ms, 표준편차 65ms, **중앙값에서 최대 133ms** (통과 기준 ±180ms 안) |
| 와이퍼 입력 (10회) | 범위 80ms, 표준편차 22ms, 중앙값에서 최대 68ms |
| 앰비언트 0.5초 간격 10회 쓰기 | 10/10 성공, 콜백 22~125ms(첫 호출 276ms). 레인 색 ARGB(주황·빨강·노랑·하늘)가 그대로 적용됨. 쓰기 후 원래 값으로 복구 확인 |
| 화면 | 전체 2560×1440. 앱 창은 오른쪽 패널(멀티윈도우) **1682×1210dp**(가로, 약 1.39:1) |
| `PARKING_BRAKE_ON`(0x11200402) | 속성 목록에 있고 읽기·구독 가능(Boolean). **그러나 에뮬레이터에서 항상 false.** 텔테일 시뮬레이터(`ParkingBrake`, `ElectronicParkingBrake`)를 켜도 값이 바뀌지 않음 |
| 일부 값만 PUT | `brake`만, `steering`만 보내도 적용됨 |

### Virtual Console REST 확인된 주소

| 입력 | 요청 | 앱이 받는 값 |
|---|---|---|
| 브레이크 | `PUT /vehicle/controls?brake=0..100` | `registerBrakePedalStatus` Boolean |
| 핸들 | `PUT /vehicle/controls?steering=<도>` (-470~500) | `registerSteeringWheelAngle` Float. **부호가 반대로 들어옴**(전송 +30 → 앱 -30, 20/20) |
| 와이퍼 | `PUT /vehicle/body?front_wiper=Off\|Auto\|Low\|High` | `registerWiperState`: Low → `ON`, Off → `OFF` |
| 주차 브레이크 | `PUT /vehicle/telltales/simulator?type=ParkingBrake&state=On&color=Red` | 앱의 `PARKING_BRAKE_ON`에는 반영되지 않음 |

### 알아 둘 점

- 와이퍼 입력 리스너(`WiperState`)의 값은 `OFF`, `ON`, `SERVICE`뿐이다. 단계(1단/2단)는 상태 변화가 올 때 `getCurrentWiperSwitch`로 읽어야 한다.
- Virtual Console 웹페이지가 1초마다 보내는 하트비트가 끊기면(탭이 백그라운드로 밀리거나 닫힘) 쓰기가 `emulator_active=false`가 되어 503으로 막힌다. 측정·시연 중에는 이 탭을 별도 창으로 띄워 두고 가려지지 않게 한다.

### 단계 1 (2026-11-13): 주차 게이트

`PUT /vehicle/gear?gear=Drive|Park`로 기어를 바꿔 측정했다(`tools/exp_gate.py`, 30회).

| 항목 | 결과 |
|---|---|
| 기어 D → 앱 화면이 숨김 상태로 전환(앱 내부 로그 `GATE_UI open=false`) | 30/30, 최소 51ms · 최대 239ms · 평균 130ms (기준 1초). 시계 오차 약 ±60ms 포함 |
| 기어 P → 게이트 열림 | 약 180~470ms. 열리면 진행하던 화면은 버리고 홈으로 돌아감(주행 중 재개 금지) |
| 첫 시도 | 앱을 막 띄운 직후 첫 두 번(별도 실행)에서 이벤트가 1초 이상 늦거나 1.6초 안에 오지 않은 적이 있었다. 이후 30회 연속 측정에서는 재현되지 않음 |

사용자에게 실제로 보이는 화면: 기어가 D이면 **Pleos OS가 앱 위에 자체 차단 화면("주행 중에는 사용할 수 없습니다.")을 먼저 띄운다.** 앱의 "주행 중에는 숨겨져요" 화면은 그 뒤에서 함께 전환된다. 앱이 `distractionOptimized`를 선언하지 않았기 때문으로 보이며, 어느 쪽이든 주행 중에는 앱 내용이 보이지 않는다. 앱 쪽 전환이 필요한 이유는 음악 정지와 차량 반응 원상 복구를 앱이 직접 해야 하기 때문이다.

### 단계 2 (2026-11-13): 게임 엔진 (debug 오토 플레이로 확인)

debug 빌드의 "오토" 버튼(모든 노트를 정확한 시각에 자동 입력)으로 3곡을 끝까지 재생했다.

| 곡 | 결과 | 이론값 |
|---|---|---|
| 천천히 한 바퀴 | PERFECT 86 / MISS 0, 롱노트 4, 92,000점, 최대 콤보 86 | 86×1000 + 4×1500 = 92,000 |
| 퇴근길 브레이크 | PERFECT 86 / MISS 0, 롱노트 4, 92,000점, 최대 콤보 86 | 92,000 |
| 충전소 페스티벌 | PERFECT 89 / MISS 0, 롱노트 4, 95,000점, 최대 콤보 89 | 89×1000 + 4×1500 = 95,000 |

- 곡 시계(재생 위치 기준)는 실제 시간과 같은 속도로 진행한다(1초 로그 기준 약 1.0배).
- 재생 요청부터 오디오가 실제로 재생되기까지 이 에뮬레이터에서 약 2.5초 걸린다. 그동안 곡 시각은 0에서 기다린다.
- **에뮬레이터 화면이 느리다.** 앱 화면이 초당 5~20프레임(중앙값 12)으로 그려진다(gfxinfo 지연 프레임 99%). 원인은 에뮬레이터 자체의 부하로 보인다: 게스트 load average 24~34, 스왑 사용, PC 여유 메모리 약 1.9GB(전체 15.3GB, qemu가 5.1GB 사용). 판정은 오디오 위치 기준 시각이라 프레임 저하와 무관하다.
- 플레이 중 기어를 D로 바꾸면 이벤트 후 약 0.3초 안에 게이트가 닫히고 재생 진행이 멈춘다. P로 돌리면 홈으로 돌아온다(재개 없음).
- **소리와 노트가 맞는지는 아직 사람이 확인하지 않았다.**

### 단계 3 (2026-11-13): 차량 입력

차량 신호(브레이크·핸들·와이퍼)를 구독해 입력 이벤트로 바꾸고, 박자 보정과 키보드 연결 프로그램을 만들었다.
입력 경로: 방향키 → `tools/key_bridge.py` → Virtual Console REST → 차량 신호 → Pleos SDK 리스너 → `InputHub` → 판정.

| 항목 | 결과 |
|---|---|
| 박자 보정 (100BPM, 브레이크 5 + 핸들 5, 자동 입력) | 동작. 브레이크 5/5, 핸들 5/5 인식, 보정값 저장·재사용 확인(브레이크 -39ms, 핸들 -39ms) |
| 핸들 입력 길이 | **80ms 짧은 펄스는 놓친다**(5회 중 2회만 인식). 핸들 신호가 약 8회/초로만 갱신되기 때문. 0.25초 유지하면 5/5. 노트는 핸들을 0.2초 이상 돌려야 안정적이다 |
| 차량 입력 → 앱 판정 (자동 입력, 천천히 한 바퀴) | 입력 86개 전부 앱에 도착. 적중률(PERFECT+GOOD) 50~65% (이 에뮬레이터에서). 아래 한계 참고 |
| 키보드 연결 프로그램 `tools/key_bridge.py` | 문법 확인만 했다. 실제 키 입력은 사람이 눌러야 해서 **아직 실행 확인 안 됨** |

**이 에뮬레이터에서 정확도를 재기 어려운 이유(측정 한계):**
- 오디오가 실제 시간보다 느리게 재생된다(곡 시계 속도 약 0.7~0.85배, 순간 추정값 0.5~0.98로 불규칙).
- 입력 이벤트가 앱 메인 스레드에서 처리되기까지 중앙값 약 200ms, 최대 약 580ms 걸린다(프레임이 느림).
- 그래서 측정 잡음이 판정 폭(±60ms)보다 커서, 입력 경로 자체의 정확도와 구분할 수 없다. 에뮬레이터가 한가할 때 측정한 단독 값(브레이크 범위 55ms, 와이퍼 80ms, 핸들 약 200ms)이 파이프라인 자체의 수치에 가깝다.
- 대응으로 입력 시각은 처리 시점이 아니라 이벤트 발생 시각을 곡 시계 모델(`SongClockModel`, 최근 재생 위치 표본에 직선을 맞춤)로 환산해 판정한다.

**더 좋은 PC에서 다시 재는 방법**
1. 에뮬레이터 실행 후 `adb forward tcp:8088 tcp:8088`, Virtual Console 페이지를 별도 창으로 열어 둔다.
2. 박자 보정: 앱에서 `보정 시작`을 누르고 `python tools/auto_player.py calib`(사람이 칠 때는 `python tools/key_bridge.py`를 켜고 방향키).
3. 곡: 앱 debug 빌드는 `adb shell am start -n com.dontstudyy.carbeat/.MainActivity --es song slow`로 곡을 미리 고를 수 있다. 곡을 시작한 뒤 `python tools/auto_player.py play slow`. 끝나면 `PLAY_RESULT` 로그(logcat 태그 `CARBEAT`)에 적중률이 나온다.
4. 노트별 판정 오차는 `JUDGE` 로그, 입력 처리 지연은 `IN` 로그에 있다.

### 단계 4 (2026-11-13): 차량 반응

곡 `퇴근길 브레이크`를 debug 오토 플레이(와이퍼 반응 켬)로 끝까지 돌리며 Virtual Console 값을 0.08초 간격으로 기록했다(`tools/watch_vehicle.py`).

| 항목 | 결과 |
|---|---|
| PERFECT → 앰비언트 | 레인 색(`#ff7a1a` `#ff3355` `#ffc233` `#4cc9ff`)으로 100%까지 올렸다가 기본 밝기로 복귀. 임의 ARGB가 그대로 적용됨 |
| 기본 밝기 | 콤보 0~9: 0%, 10 이상 30%, 30 이상 55%, 50 이상 80% 확인 |
| MISS → 앰비언트 끔 | 밝기 0%(`#ffffff 0%`)로 꺼지고, 다음 판정이 나오면 복귀 |
| 와이퍼 | 콤보 10, 20에서 `Off → Low`(1단), 약 1.1초 뒤 `Low → Off`. 곡당 2회만. 와이퍼 반응을 끄면(기본값) 움직이지 않음. 왼쪽 차량 클러스터에도 와이퍼 모드(저속)가 표시됨 |
| 완주 → 실내등 | ON/OFF 3회(0.5초 간격) |
| 원상 복구 | 곡 종료 뒤 앰비언트 `#00e5ff 100%`, 와이퍼 Off, 실내등 꺼짐으로 시작 값과 같음. 플레이 중 기어 D로 바꾸면 4초 안에(실제로는 즉시) 같은 값으로 복구 |
| 쓰기 빈도 | 앰비언트 쓰기 간격 최소 약 0.34초(초당 3회 미만), 밀리면 최신 명령만 남김 |
| 차량 반응 설정 끄기 | 켜짐/꺼짐 확인. 끄면 차량 값이 바뀌지 않고 게임만 진행 |
| 실내 그림·신호 띠 | 차량에서 읽은 값(브레이크·핸들·와이퍼 리스너, 앰비언트·실내등은 차량 리스너와 쓰기 콜백)으로 그림 |

**알아 둘 점**
- **앰비언트 스위치 API는 쓰지 않는다.** `setAmbientLightSwitch`는 쓰기 콜백이 성공하고 SDK가 읽는 값도 바뀌지만 Virtual Console의 앰비언트 모드(`On`)에는 반영되지 않는다. SDK가 읽는 앰비언트 상태도 Virtual Console과 달리 항상 OFF였다. 그래서 "앰비언트 끔"은 밝기 0으로 구현했고, 복구도 색·밝기만 한다.
- 앱 프로세스가 강제 종료되면(`force-stop`, 크래시) 되돌릴 방법이 없다. 정상 종료·중단·주행 전환·앱 종료(`onDestroy`)에서는 복구한다.
- 곡 안에서 와이퍼 입력 변환은 앱이 켠 와이퍼를 1.5초 동안 무시한다(`WiperConverter.markAppAction`).
